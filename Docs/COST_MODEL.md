# Модель себестоимости блока (`cost/model/`)

Слой норм между техническим расчётом БВР и экономикой Cost V2. Принцип
один: **нормы — в коде, цены — в справочниках**. Код считает натуральные
величины по инженерным формулам, справочники умножают их на ставки,
надбавки применяются отдельным шагом.

## Граница «норма / цена»

| Что | Где живёт | Пример |
| --- | --- | --- |
| Нелинейная формула, дающая натуральную величину | `cost/model/` | смены станка = погонаж / коммерческую скорость |
| Параметр формулы | справочник | техническая скорость 12 м/ч, ресурс коронки 700 м |
| Цена за единицу драйвера | `cost_rules`, `material_prices`, `labor_rates`, `subcontract_rates` | 46 ₽/кг гранулита |
| Ставки и надбавки организации | `organization_rates` | взносы 30 %, ОХР 10 %, НДС 20 % |
| Параметр моделирования | вкладка «Экономика» | плановый объём юнита, смены станка, состав бригады |

Новая статья вида «цена × существующий драйвер» — это запись в
`cost_rules`, а не код. Код нужен только для **нового типа натуральной
величины**.

## Что откуда берётся

```
технический паспорт (physical + lineage)
        ↓
cost/model: drilling → logistics → materials → labor → equipment → cost_rules → unit
        ↓
строки CostLine по слоям variable → project_direct → production → full
        ↓
markup: ОХР → рентабельность → НДС
        ↓
четыре цены м³: marginal, full, with_margin, with_vat
```

Порядок модулей важен: смены станка и СЗМ выводятся первыми, потому что от
них зависят человеко-смены бригады и затраты техники. `materials` считает ВМ
и средства инициирования по выбранной на вкладке номенклатуре — количество
из паспорта, цена из «Стоимости материалов»; правило затрат по тому же
драйверу уступает выбору, а пока выбора или цены нет — остаётся запасным
путём, и модель сообщает, по какому из них посчитана статья.

## Натуральные величины

| Величина | Формула | Модуль |
| --- | --- | --- |
| `v_commercial_m_per_shift` | `tech_speed × (shift_hours − unproductive_h)` | `drilling` |
| `rig_shifts` | `drilling_m / v_commercial` | `drilling` |
| `rig_maintenance_shifts` | `rig_shifts × maintenance_ratio` | `drilling` |
| `rig_plan_metres` | `rig_plan_shifts × v_commercial` | `drilling` |
| `szm_trips`, `szm_shifts` | `⌈bulk_kg / грузоподъёмность⌉`, один рейс — одна смена | `logistics` |
| `delivery_trips`, `delivery_shifts` | то же по патронам | `logistics` |
| `vm_tkm` | `cartridge_kg / 1000 × расстояние от склада` | `logistics` |
| `component_tkm` | `bulk_kg / 1000 × расстояние от базы` | `logistics` |
| `mobilization_trip_km` | `плечо × 2 / блоков на мобилизацию` | `logistics` |
| `crew_shifts.<должность>` | ручная поправка → смены техники → `норм_смен / норм_операций` | `labor` |
| `crew_per_shift.<должность>` | человек в смене из состава бригады; `0` — один человек | `labor` |
| `crew_rotation.<должность>` | `⌈плановые смены техники × человек в смене / норм_смен человека⌉`, только экипаж техники | `labor` |
| `warehouse_area_m2` | `⌈max(потребность месяца / ёмкость на м²)⌉` | `unit` |
| `unit_allocation_share` | `объём блока / плановый объём юнита` | `unit` |

У каждой величины есть `lineage` — строка, объясняющая, откуда она взялась:
именно её видит пользователь рядом с числом.

## Слои себестоимости

- `variable` — растёт вместе с объёмом: ВМ, оснастка, ДТ, запчасти.
- `project_direct` — прямые затраты блока: ФОТ со взносами, амортизация и
  ТОиР техники по сменам, мобилизация. ТОиР и запчасти техники могут
  считаться по возрасту машины — ступень шкалы типа техники в процентах от
  первоначальной стоимости (`cost/model/age_scale.py`, `Docs/REFERENCES_MODEL.md`).
- `production` — постоянные затраты юнита, распределённые по плановому
  объёму: косвенный персонал, база, аренда склада ВМ.
- `full` — то, что на блок не распределяется: например, постоянные затраты
  собственного станка при бурении на субподряде.

Итоги накопительные: `full` включает все предыдущие слои. Маржинальная цена
считается по `project_direct`, полная — по `full`.

## Распределение постоянных затрат

База — **плановый объём юнита**, параметр вкладки, а не справочник. Только
он показывает, как доля постоянных затрат в цене м³ падает с ростом
загрузки: при плане 400 000 м³ вместо 600 000 полная цена растёт, а
маржинальная не меняется.

Постоянные затраты техники распределяются по её **плановым сменам**: при 25
сменах станка вместо 40 постоянная часть метра растёт на 60 %, а штат
бурильщиков на ротацию падает с трёх до двух — смена станка стоит 4 800 ₽
оклада вместо 4 500 (60 000 × 2 / 25 против 60 000 × 3 / 40).

Постоянная затрата юнита может быть закреплена за операцией
(`unit_fixed_costs.operation_code`): механик, мастер и слесарь буровых —
«Бурение». Сумма и распределение по плановому объёму те же, но строка несёт
код операции, и её доля входит в себестоимость метра бурения (лист «Расчёт»,
панель цены метра на «Бурении»). Операции нет в пакете — строка остаётся
общей затратой юнита.

## ФОТ прямого персонала

Численность в модели двух видов:

- **человек в смене** `h` — поле `headcount` состава бригады
  (`crew_templates.members`, параметр вкладки `crew`): сколько людей должности
  одновременно работает в одной смене. `0` — один человек;
- **штат на ротацию** `N` — модель выводит только для экипажа техники
  (станок, СЗМ, доставщик ВМ, тягач эмульсии):
  `N = ⌈плановые смены техники × h / норм_смен человека⌉`. Плановые смены —
  та же база, что у амортизации машины: станок — `rig_plan_shifts` (пусто и 0 —
  норматив типа), остальная техника — `machine_plan_shifts`.

Строка `LABOR_<должность>`, `S` — смены на блок, `M` — оклад из «Ставок
персонала», `n` — норма смен должности:

| Часть | Экипаж техники | Остальные должности и техника без плана |
| --- | --- | --- |
| Оклад | `M × N / плановые смены × S` | `M / n × S × h` |
| Сделка | `расценка × драйвер / piece_unit × h` | то же |
| Суточные | `S × h × суточные` (`LABOR_PER_DIEM`, строка на операцию) | то же |
| Проживание и питание | `S × h × (проживание + питание)` (`CAMP_<операция>`) | то же |

Должность со сменами на блок (`positions.shifts_per_block`: слесарь, механик
участка) — персонал участка, а не экипаж техники: `S` берётся из этого поля, а не
у станка, оклад — `M / n × S × h` без штата ротации, методика ФОТ её не берёт
(`block_payroll.block_crew`). С операцией бурения её строка входит в цену метра,
а на панели цены метра — в группу «ФОТ ИТР и ремонтного персонала» с бегунком
оклада.

Взносы и резерв отпусков начисляются на сумму строк каждой операции
(`LABOR_CONTRIBUTIONS`, `LABOR_VACATION_RESERVE`, подпись «…: <операция>»), суточные —
тоже строкой на операцию: доля экипажа и персонала бурения входит в цену метра
бурения, а сумма по блоку та же, что у одной общей строки. При `salary_basis = NET`
строка ФОТ делится на `1 − НДФЛ`. Штат на ротацию входит только в месячный оклад:
метры блока бурит смена, поэтому сделка, суточные, проживание и питание идут
людям в смене. Проживание и питание — не ФОТ (взносов на них нет): строка на
каждую операцию, где работают люди, и для должностей методики ФОТ тоже, так что
доля экипажа станка входит в цену метра бурения. Если у
выбранной техники нет плановых смен, модель предупреждает и считает оклад по
норме смен должности. Если количество, за которое платится сделка, в паспорте
блока не задано или равно нулю (незаполненное поле паспорт пишет нулём),
сделка не начисляется, и модель предупреждает. В формуле строки объём
сделки подписан единицей (м³, кг, п.м., шт), а не именем драйвера.

Пример (`tests/model_fixtures.py`): бурильщик, 60 000 ₽/мес, норма 15 смен,
станок 40 плановых смен, 13 953,49 м за 116,28 смены, расценка 150 ₽/м.
`N = ⌈40 / 15⌉ = 3`; оклад `60 000 × 3 / 40 × 116,28 = 523 255,81 ₽`; сделка
`150 × 13 953,49 = 2 093 023,26 ₽`; строка 2 616 279,07 ₽. До TASK-010 PR 0b
оклад и сделка умножались на штат ротации — 7 674 418,60 ₽.

Строка чувствительности «Численность бригады» умножает на 0,9 и 1,1 уже
посчитанные `h` и `N` (параметр модели `crew_scale`), а не поле состава:
штат не округляется заново, и ФОТ блока меняется ровно на ±10 %. Иначе у
водителя СЗМ с одним человеком в смене +10 % давали бы `⌈1,1⌉ = 2` и двойной
оклад, −10 % — прежний, а бурильщик с `0` в составе в переборе не участвовал бы.

Методика ФОТ по объектам (оклад, сдельная премия по шкале, отчисления и резервы по дням) — отдельная модель,
`Docs/PAYROLL_MODEL.md`. Блок переходит на неё параметром вкладки `payroll_source`:
`RATES` (по умолчанию) — ФОТ по ставкам, как описано выше; `PAYROLL` — экипаж
бурения (машинист, помощник) считается по методике (`cost/model/block_payroll.py`,
раздел «Экономика блока» в `Docs/PAYROLL_MODEL.md`), его строки `LABOR_<должность>`
помечены происхождением `PAYROLL`, а `labor` их пропускает; остальные должности
остаются на ставках. Результат сохранённого прогона получает блок `payroll`.

Длительность смены берётся одним резолвером `ModelContext.shift_hours`: поле
`shift_hours` объекта работ (`sites.shift_hours`), если оно задано и больше нуля,
иначе `shift_hours` из «Ставок и надбавок организации» (умолчание 11 ч). Оно
одинаково входит в `v_commercial` бурения и в часы логистики (топливо рейсов).

## Склад ВМ

Аренда склада — не константа на блок, а ресурсный пул с ёмкостью:
`resource_kind = STORAGE_AREA`, `consumption_norms` вида
`{"driver": "downhole_nsi", "units_per_capacity": 300}`. Требуемая площадь
считается по месячному плану юнита; превышение базовой ёмкости добавляет
ступени аренды и предупреждение с требуемой площадью.

## Происхождение величин

Каждая строка `CostLine` несёт два поля происхождения —
`quantity_origin` и `price_origin` (`cost/v2/models.py`), тип
`ValueOrigin = Literal["PASSPORT", "CALC", "REFERENCE", "NORM", "MANUAL", ""]`:

| Значение | Смысл |
| --- | --- |
| `PASSPORT` | величина взята из технического паспорта блока (например, метраж бурения, масса ВВ) |
| `CALC` | посчитано моделью себестоимости (смены техники, амортизация на смену) |
| `REFERENCE` | цена взята из опубликованной ревизии справочников |
| `NORM` | норматив справочника, сметчик его не менял (например, плановые смены по шаблону пакета) |
| `MANUAL` | введено сметчиком на вкладке вручную |
| `""` (пусто) | у величины нет происхождения (например, у доли постоянных затрат юнита нет «количества») |

Поле проставляет модуль, который создаёт строку (`materials.py`,
`drilling.py`, `labor.py`, `equipment.py`, `logistics.py`, `services.py`,
`unit.py`) через `ModelContext.add_line(..., quantity_origin=..., price_origin=...)`
— вызывающий код (интерфейс) ничего не выводит по формуле или тексту,
только читает готовое поле. Общее правило по модулям: количество из
паспорта → `PASSPORT`; количество, посчитанное по формуле, → `CALC`; смены
или численность, заданные вручную, → `MANUAL`, иначе — `NORM`; цена из
справочника → `REFERENCE`; ручная цена (например, ставка субподряда,
проверяемая до публикации) → `MANUAL`.

## Цена метра бурения для листа «Расчёт»

Блок 1.2 листа «Расчёт» (смета по сценарию, `POST /cost/calculate`) берёт цену
метра у той же модели, что и «Экономика блока» (TASK-010, PR 3); Excel-калькулятор
`cost/drilling.py` и `POST /cost/drilling-unit` удалены. У листа нет сохранённого
паспорта, поэтому модель запускается на снимке из погонажа бурения и объёма
блока (`cost/model/drilling_price.py`; объём нужен субподряду — доле
нераспределённых постоянных собственного станка в плановом объёме юнита); станок, порода, объект, экипаж,
режим ФОТ и надбавки берутся из параметров активного черновика сметы
(`context.drilling_model.parameters`, фронт — `useBlockEconomicsSession`).
Ревизия справочников — `parameters.reference_revision_id`, пустая — актуальная.

    цена метра = Σ строк PRODUCTION_DRILLING / метры × (1 + ОХР) × (1 + рентабельность)

В сумму входят строки модели бурения (оснастка, ДТ, запчасти, амортизация и
страховка станка, ТО), ФОТ экипажа бурения (ставки или методика — по
`payroll_source`), проживание и питание экипажа станка на вахте
(`CAMP_PRODUCTION_DRILLING`, в обоих режимах ФОТ), доля постоянных затрат юнита,
закреплённых за бурением (механик, мастер, слесарь — `unit_fixed_costs.operation_code`),
строки правил затрат и услуг этой операции, а также взносы, резерв отпусков и
суточные на ФОТ бурения, начисленный по ставкам (у должностей методики ФОТ они
уже внутри её строки). Цена метра для доли в марже (`block_margin.margin`,
только при методике ФОТ) — та же сумма строк с теми же надбавками. У субподряда в сумму входит тариф за метр; персонал юнита, закреплённый
за бурением, тогда остаётся общей затратой юнита (свой участок на блоке не
работает).

Нет черновика сметы, станка в нём или нормы бурения у станка — цена нулевая, а
причина уходит в `notes` результата; молчаливого отката на другой расчёт нет.
Для расчётов «Проектирования», у которых вкладки «Экономика» нет (смета проекта,
сценарии, рекомендации, оптимизация), сервер берёт параметры «как у нового
черновика» (`drilling_price.default_source`): первый буровой станок справочника,
шаблон экипажа пакета, ставки организации, объект по имени (иначе первый).

Колонка `workspace`-сценария `drilling_calculator_input` осталась в таблице, но
код её не читает и не пишет (удаление колонки — отдельная миграция).

## Что двигает цену метра («что если» на странице «Бурение»)

`cost/model/drilling_sensitivity.py` отвечает на вопрос страницы «Бурение»,
какие ручки сильнее всего двигают стоимость метра собственного бурения, и
даёт покрутить их, не меняя ни черновик, ни справочники.

Две цены — себестоимость метра без ОХР и рентабельности (`Prices`), по всем
строкам операций бурения, как цена метра листа «Расчёт» (`drilling_price`):

    с ФОТ   = Σ строк операций бурения / drilling_m
    без ФОТ = с ФОТ − (ФОТ экипажа + ФОТ ИТР и ремонтного персонала
                       + взносы и резерв отпусков) / drilling_m

Без услуг и закреплённого за бурением персонала «без ФОТ» равна
`drilling_rub_per_m`. Строки ФОТ экипажа — ставки или методика по
`payroll_source`; взносы, резерв отпусков и суточные ставок — строки операции
бурения и входят в цену, как на листе «Расчёт». При субподряде, без метров или без нормы бурения обе цены —
`null`.

Вместе с ценами `Prices` несёт слагаемые метра для кольца (`components`, в
сумме — цена с ФОТ):

- статьи станка — `DRILL_*` строк самой модели бурения
  (`BlockEconomics.drilling_lines`, по тождеству объекта), кроме выпуска на
  линию и медосмотра;
- `RIG_RULES` «Станок: затраты по правилам» — правила затрат операций бурения
  со статьёй станка (`DRILL_*`, например доп. оснастка): это затрата станка, но
  не строка модели, поэтому отдельно от `drilling_rub_per_m`;
- `SERVICES` «Услуги сторонних организаций» — выпуск на линию и медосмотр,
  прочие правила затрат и ручные услуги операций бурения (трал);
- `CAMP` «Проживание и питание экипажа» — строка `CAMP_<операция бурения>`
  (не ФОТ: в «без ФОТ» остаётся);
- `CREW_PAYROLL` «ФОТ экипажа» — строки `LABOR_*` и суточные `LABOR_PER_DIEM`;
- `SITE_STAFF` «ФОТ ИТР и ремонтного персонала» — косвенный персонал юнита,
  закреплённый за бурением, и строки ФОТ должностей со сменами на блок;
- `PAYROLL_CHARGES` «Страховые взносы и резерв отпусков» — `LABOR_CONTRIBUTIONS`
  и `LABOR_VACATION_RESERVE` операций бурения (ФОТ: «без ФОТ» их не содержит);
  `UNIT_FIXED` — прочие такие затраты юнита.

У групп есть подстатьи `parts` — по паре «статья, название строки» (два
правила с одной статьёй — разные строки), с подписью без префикса «ФОТ: » или
категории; у ФОТ экипажа с одной должностью подстрок нет. И кривую премии
машиниста (`premium_curve`: шкала ставки из снимка с подменами через
`payroll_inputs._scale` и те же точки `scale_series`, что у `payroll.series`;
плановый темп — из блока `payroll`, когда методика применилась).

Ручки участка (`group = "site"`, `_site_knobs`) показываются все, не по силе:
ставка или сумма правил затрат операций бурения (`RULE:<код>`), сумма ручных
услуг бурения вкладки (`SERVICE:<код услуги>` — по названию, как строка сметы,
чтобы правка списка услуг не переносила подмену на соседнюю), выпуск на линию и медосмотр станка,
оклад должности каждого косвенного персонала юнита, закреплённого за бурением
(`STAFF:<код ставки>`), проживание и питание (`LODGING`, `MEALS`, только на
вахтовом объекте). Нулевая ставка — нет ручки. У сумм «на блок» (правило с
постоянной суммой, ручная услуга на блок) бегунок свой: шаг — пятая часть суммы,
округлённая до 1/2/5 × 10ⁿ (100 000 ₽ → 20 000 ₽), диапазон — от шага до
двойной суммы (`step`, `span` ручки); у остальных — ±30 % с «круглым» шагом.

Ручки (`knobs`) собираются по параметрам черновика: техническая скорость и
непроизводительное время выбранного условия бурения (`pick_condition`),
стойкость и цена коронки, ППУ и штанг (`TOOLING_PARTS`, цена — действующая
запись прайс-листа; подмена пишет `price_rub` во все записи материала и
обнуляет `delivery_rub`, чтобы цена с доставкой равнялась пробной), цена ДТ
объекта, плановые смены станка (`draft_param = true` — у них свой бегунок
черновика, пробного нет). Множителя численности экипажа среди ручек нет: это
не параметр блока, состав экипажа задаётся в смете. Чего нет
в справочниках — нет и ручки. Чувствительность (`compute`) — ±10 % по каждой,
два прогона движка, сортировка по |Δ| цены с ФОТ экипажа; премия в
ранжирование не входит, а её плечи сжаты правилами шкалы по соседним ручкам
(`premium_bounds`: потолок выше нормы, расценка на потолке не ниже расценки на
норме) — иначе недопустимая шкала откатила бы методику на ставки, и «эффект
премии» мерил бы смену способа расчёта; плечо на границе — базовая цена.

Премия машинистов (`premium`) — шкала ставки без условия бурения первой
должности экипажа бурения, которая платится сдельно за приведённые метры
(`pays_by_meters`, как у `block_payroll`) и имеет `scale_type` (`_labor_rate`): у кривой — норма,
расценка на норме, потолок, расценка на потолке; у ступеней — расценка каждой
ступени (`PREMIUM_TIER_RATE_<i>`). Шкала двигает цену только при
`payroll_source = PAYROLL`, своих силах и реально применившейся методике
(`payroll_applied` базового прогона); иначе `applies = false` с пояснением,
ручки отдаются с нулевой дельтой без прогонов.

«Что если» (`what_if`, `apply_overrides`) подменяет абсолютные значения ручек
в копии снимка (`dataclasses.replace`, записи не меняются на месте) и считает
обе цены на базе и с подменами. Неизвестная ручка, значение не больше нуля или
шкала, нарушающая `LaborRatePayload` (потолок не выше нормы, расценка на
потолке ниже расценки на норме), — `WhatIfError`; API отдаёт 422 с текстом
проверки справочника. Маршруты — `POST /economics/block-economics/drilling-sensitivity`
и `POST /economics/block-economics/drilling-what-if` (`require_internal_access`,
без `require_human`: ничего не сохраняется). Экран — `Docs/BLOCK_ECONOMICS_UI.md`,
«Что двигает цену метра».

## Субподряд бурения

При исполнении `drilling_executor = "SUBCONTRACTOR"` ставку за метр выбирает
`cost/model/drilling.py:_subcontract_rate` по приоритету:

1. **Ручная ставка** — `ModelParameters.subcontract_rate_rub`, если задана;
   `price_origin = "MANUAL"`. Сметчик проверяет предложение подрядчика, ещё
   не заведённого в справочник; в справочник ставка попадает только явной
   кнопкой «Сохранить тариф в справочник»
   (`POST /economics/subcontract-rates/to-reference`), никогда — автоматически
   из расчёта.
2. **Выбранный тариф** — запись `subcontract_rates` с кодом
   `ModelParameters.subcontract_rate_code`, если ручной ставки нет;
   `price_origin = "REFERENCE"`. Незнакомый код (запись отсутствует или
   неактивна) не считается ошибкой — модель выдаёт предупреждение и
   переходит к следующему шагу.
3. **Первая запись по операции** — первая активная запись
   `subcontract_rates` с `operation_code == "PRODUCTION_DRILLING"` (прежнее
   поведение до появления выбора тарифа); `price_origin = "REFERENCE"`.
4. **Ноль с предупреждением** — если подходящей записи нет вовсе: строка
   `DRILL_SUBCONTRACT` считается нулевой, а не падает исключением.

Метраж бурения (`quantity`) в любом случае берётся из паспорта —
`quantity_origin = "PASSPORT"`.

## Отсутствующие данные

Незаполненная запись справочника — не исключение, а предупреждение и нулевая
строка. Список предупреждений возвращается вместе с результатом и
показывается на вкладке: сметчик должен увидеть незаполненное место, а не
ошибку 500.

## Хранение и сравнение

Каждый прогон сохраняется в `blastex.economics_runs` целиком: паспорт,
пакет, ревизия справочников, параметры и результат. Сравнение сценариев идёт
между снимками, поэтому старый расчёт воспроизводим спустя месяцы, даже если
справочники изменились.

Поэтому удаление технического паспорта — время в `deleted_at`, а не `DELETE`
строки: на паспорт ссылаются прогоны экономики, событийные расчёты и блоки
проектов (везде FK RESTRICT), и они переживают удаление. Удалённый паспорт
пропадает из списков (`GET /economics/technical-passports`) и не принимает
новых записей — попытка посчитать по нему или выпустить следующую версию
даёт 409, — но читается по идентификатору, чтобы сохранённый прогон
открывался вместе со своим паспортом.
