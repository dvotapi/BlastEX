# Калибровки ML и пометки старой модели (PR 3) — спецификация

Дата: 2026-09-30. Базовый коммит: `b59e9e0` (ветка `feat/fragmentation-cunningham-engine`,
PR #101 на момент написания не слит). Родительская спека —
`Docs/plans/2026-09-29-fragmentation-engine-cunningham-design.md` (разделы 4.4–4.6, 8);
план PR 2 — `Docs/plans/2026-09-30-fragmentation-cunningham-pr2-engine.md`
(отступления № 2 и № 7 закрываются здесь).

## 1. Зачем

После PR 2 движок «Проектирования» считает кусковатость на новой базе
(фактор A и x50 по Каннингему, модели `kuznetsov`, `kuzram`, `swebrec` версии
2.0.0). ML-калибровки, пространственные модели и снимки датасетов по-прежнему
живут на старой базе Kuz-Ram 1.0.0, а защита от смешения — временные заглушки
PR 2 (`CALIBRATION_BASELINE_MODEL`, `_old_base`, проверка `is_legacy_model` в
сценариях).

**Критерий успеха:**

1. Каждая калибровка знает базу, на которой обучена, и применяется только к
   прогнозу той же базы; иначе — baseline без поправки и предупреждение
   «нужно переобучить». Ни одного пути, где поправка молча ложится на чужую
   формулу.
2. Калибровку на новой базе можно обучить сразу после выката, на истории
   площадки, без ожидания новых взрывов.
3. Прогноз, посчитанный старой моделью, в интерфейсе и паспорте помечен
   «старая модель».

## 2. Решения владельца (2026-09-30)

Действуют решения 2026-09-28 из родительской спеки (сохранённое не
пересчитывается; старые калибровки к новым прогнозам не применяются; настройки —
из объекта работ). Новые:

1. **Заплатка в PR 2.** Путь `POST /calibration/predict` с присланным клиентом
   baseline закрывается ещё до слияния #101 (раздел 3.1): иначе сразу после
   выката PR 2 калибровка из панели ляжет на прогноз 2.0.0.
2. **Baseline новой базы пересчитывается при сборке снимка датасета.**
   Сохранённый прогноз остаётся в строке как есть, с моделью и версией; рядом
   пишется baseline, посчитанный текущей базой. Старые снимки не трогаются.
3. **Старые калибровки работают только со старыми моделями.** Артефакты не
   переписываются, статус production не снимается; к моделям `*_legacy`
   поправка применяется как раньше, к новым — нет. Обучение калибровки
   кусковатости на старом снимке запрещено: «соберите новый снимок».
4. **Подход A:** база хранится в артефакте, совместимость решает одна функция,
   которую зовут все точки применения.

## 3. Как устроено сейчас (на `b59e9e0`)

- Артефакт калибровки `CalibrationModel` (`intelligence/calibration/types.py:122`)
  — файлы `data/teams/{team}/calibration/{id}.json` и `.joblib`, запись один раз,
  контрольная сумма по всему JSON без `integrity_sha256`, `status`,
  `status_updated_at` (`intelligence/calibration/persistence.py:62`). Базы нет,
  в `MODEL_SPECS` (`types.py:52`) — только строка `baseline_source: "kuzram"`.
- Обучение (`intelligence/calibration/training.py:77`) берёт baseline из снимка:
  `targets["FRAGMENTATION"]["predicted_x50_mm"]` (`intelligence/calibration/features.py:57`).
- В снимок `predicted_x50_mm` попадает из сохранённого прогноза результата
  взрыва (`intelligence/datasets/targets.py:24`); модель и версия прогноза не
  копируются, поэтому в старых снимках базу строки не определить.
- Применение:
  - `POST /calibration/predict` (`api/services/calibration_service.py:137`):
    присланный baseline принимается как `provided` без проверок; фронт шлёт x50
    текущей модели панели (`frontend/src/pages/design/DesignPage.tsx:1495`);
    без baseline — `empirical_baseline` (`intelligence/calibration/prediction.py:180`);
  - сценарии — `api/services/scenario_service.py::_apply_ml_overlays`;
  - дрейф — `intelligence/drift/scoring.py:77`, baseline из снимка без проверки
    базы.
- Пространственная модель `SpatialModel` (`intelligence/spatial/types.py:369`)
  обучается на скважинной «физике», замороженной в снимке
  (`intelligence/datasets/builder.py:23`), а при применении
  (`intelligence/spatial/prediction.py:73`) считает физику заново по живому
  паспорту — обе стороны сейчас моделью `kuzram_legacy`.
- Подпись «старая модель» (`simulation/fragmentation/base.py:111`,
  `settings_source_label`) смотрит только на суффикс `_legacy`: прогноз
  `kuzram 1.0.0`, сохранённый до PR 2, пометки не получает.

## 4. Что меняется

### 4.1. Заплатка в PR 2 (до слияния #101)

- `CalibrationPredictRequest` (`api/schemas/calibration.py:128`) получает
  необязательные `baseline_model: str` и `baseline_model_version: str`.
- Фронт (`DesignPage.tsx::overlayBaseline` и вызов) шлёт их из
  `fragResult` вместе с baseline кусковатости.
- Сервер: для `kuzram_residual` и `oversize_residual` присланный baseline
  принимается, только если он посчитан старой базой; иначе, а также если модель
  не указана, поправка не применяется и ответ несёт предупреждение
  «Калибровка обучена на старой модели Kuz-Ram 1.0.0 и к прогнозу новой модели
  не применяется — её нужно переобучить.» `ppv_residual` не затрагивается.

В PR 3 эта проверка переходит на функцию совместимости (4.3).

### 4.2. База в артефактах

Новый модуль `intelligence/calibration/base.py`:

```python
@dataclass(frozen=True)
class FragmentationBase:
    model: str            # идентификатор модели движка, например "kuzram"
    model_version: str    # "2.0.0"

LEGACY_BASE = FragmentationBase("kuzram_legacy", "1.0.0")
CURRENT_BASE = FragmentationBase("kuzram", <MODEL_VERSION модуля kuzram>)
```

- `CalibrationModel` получает поля `baseline_model` и `baseline_model_version`
  (пустые по умолчанию). `from_dict` терпит их отсутствие. Пустые поля у
  калибровки кусковатости означают `LEGACY_BASE`. Старый JSON не
  переписывается: контрольная сумма считается по сохранённому payload
  (`persistence.py:146`), а смена статуса правит сырой JSON, не `to_dict`
  (`persistence.py:215`), — поэтому новые ключи в `to_dict` старым файлам не
  мешают. Тест закрепляет: фикстура артефакта до PR 3 грузится и меняет статус.
- `SpatialModel` получает те же два поля с тем же правилом.
- `CalibrationPrediction` и ответ пространственного прогноза несут базу
  артефакта в `provenance`.

### 4.3. Функция совместимости

```python
def compatible(model_type: str, artifact: FragmentationBase,
               prediction: FragmentationBase) -> bool: ...
def base_of(model: str, version: str) -> FragmentationBase: ...
def is_old_model(model: str, version: str) -> bool: ...
```

- База прогноза: модели `*_legacy` и любая модель с версией ниже 2.0.0 (или
  пустой версией) — старая база; модели 2.x — новая.
- `kuzram_residual` (x50): совместим с любой моделью той же базы — у трёх
  моделей одной базы x50 одинаковый.
- `oversize_residual`: только та же модель и версия (негабарит зависит от
  кривой). Для старого артефакта «та же модель» — `kuzram` 1.0.0 или
  `kuzram_legacy`.
- Несовместимо — поправка не применяется, возвращается baseline без изменений
  и предупреждение с обеими базами, например: «Калибровка обучена на Kuz-Ram
  1.0.0 (старая модель) и к прогнозу Kuz-Ram 2.0.0 не применяется — её нужно
  переобучить.»

Подписи баз в сообщениях берутся из реестра моделей движка, а не пишутся
вручную.

### 4.4. Снимок датасета

Строка цели `FRAGMENTATION` новых снимков (`intelligence/datasets/targets.py`)
получает:

| Поле | Смысл |
|---|---|
| `predicted_model`, `predicted_model_version` | модель сохранённого прогноза (сам прогноз — как был) |
| `baseline_x50_mm`, `baseline_oversize_pct` | baseline текущей базы, пересчитанный при сборке |
| `baseline_model`, `baseline_model_version` | база пересчёта (`kuzram`, 2.0.0) |
| `baseline_settings` | снимок применённых настроек с источником (формат `provenance.settings`) |
| `baseline_warnings` | предупреждения пересчёта |

Пересчёт — движком (`predict_design`, модель `kuzram`) по паспорту взрыва:

- порода и ВВ — из входных величин сохранённого прогноза
  (`provenance.inputs`), то есть то, что видел инженер; без сохранённого
  прогноза — умолчания, как сейчас в `_compute_empirical`, и предупреждение;
- настройки модели — снимок `provenance.settings` сохранённого прогноза, иначе
  объект работ по правилу PR 2 (`api/services/fragmentation_settings.py`:
  объект → активный объект организации → умолчания);
- не посчиталось — `baseline_*` пустые, предупреждение; строка остаётся в
  снимке, но в обучение калибровки кусковатости не идёт.

Расчётный слой в базу не ходит: сервис датасетов разрешает настройки и
передаёт их сборщику.

Скважинная «физика» новых снимков (`_extract_snapshot_holes`) считается той же
базой и теми же настройками; снимок хранит её базу рядом со скважинами.

### 4.5. Обучение

- Калибровки кусковатости новых снимков учатся на `baseline_x50_mm` /
  `baseline_oversize_pct`; база снимка записывается в артефакт.
- Снимок без `baseline_model` (собран до PR 3) для `kuzram_residual` и
  `oversize_residual` — ошибка обучения «Снимок собран до перехода на новую
  модель кусковатости — соберите новый снимок». `ppv_residual` учится как
  раньше.
- Пространственная модель: база снимка записывается в артефакт; снимок без
  базы даёт артефакт со старой базой (решение для пространственной модели —
  4.6).

### 4.6. Точки применения

1. **`POST /calibration/predict`.**
   - Baseline прислан: нужна его модель и версия; сверка по 4.3. Без модели —
     поправка не применяется, предупреждение.
   - Baseline не прислан: сервер считает его базой артефакта. Сохранённый
     прогноз паспорта берётся, если его база совместима; иначе пересчёт моделью
     базы артефакта с настройками из снимка сохранённого прогноза, иначе —
     объект работ, иначе умолчания. `CALIBRATION_BASELINE_MODEL` и `_old_base`
     удаляются.
2. **Сценарии** (`_apply_ml_overlays`): после загрузки артефакта — сверка базы
   артефакта с базой модели сценария (`params.fragmentation_model` и её
   версия из реестра). Касается и выбранной калибровки, и production-режима.
   Проверка `is_legacy_model` PR 2 удаляется.
3. **Дрейф** (`_score_calibration`): новый артефакт читает `baseline_*` строки;
   старый — `predicted_*` только старой базы (строки старых снимков считаются
   старой базой). Строка без подходящего поля пропускается.
4. **Пространственная модель:** `apply_model` считает физику базой своего
   артефакта (с настройками, разрешёнными `spatial_service` по правилу PR 2);
   без артефакта — текущей базой. Отказа нет: пространственная модель не
   накладывается на прогноз панели, а считает свой; ответ несёт базу и метку
   «старая база».

### 4.7. Пометки

- `is_old_model` (4.3) — единственное правило «старая модель» на сервере.
  `settings_source_label` получает версию: у сохранённого прогноза
  `kuzram 1.0.0` подпись «Старая модель: …», как у `*_legacy`. Панель
  «Кусковатость» и HTML-паспорт показывают готовую подпись, своей логики у
  фронта нет.
- Панель калибровок (`frontend/src/pages/design/CalibrationPanel.tsx`): в
  списке и карточке — «База: Kuz-Ram 2.0.0» или «старая база — только для
  старых моделей» (подпись приходит с сервера в ответе списка/карточки);
  предупреждение отказа — из `warnings` ответа прогноза.
- Пространственный слой — метка «старая база» у модели, обученной до PR 3.

## 5. Совместимость сохранённых данных

- Артефакты калибровок и пространственных моделей, снимки датасетов не
  переписываются; грузятся с прежней контрольной суммой.
- Сохранённые прогнозы паспортов не пересчитываются.
- Миграций базы нет: всё ML-хранилище — файлы в `data/teams`.

## 6. Тесты

Новые:

- старый артефакт + прогноз 2.0.0 → поправки нет, предупреждение
  «переобучить»; старый артефакт + `kuzram_legacy` → поправка как раньше;
- x50-калибровка на базе 2.0.0 + прогноз `swebrec` 2.0.0 → применяется;
  калибровка негабарита на `kuzram` 2.0.0 + `swebrec` 2.0.0 → нет;
- присланный baseline без модели → поправки нет;
- baseline не прислан: старый артефакт считает `kuzram_legacy`, новый —
  `kuzram` 2.0.0 с настройками из снимка сохранённого прогноза;
- новый снимок несёт `predicted_model*`, `baseline_*` и снимок настроек;
  сохранённый прогноз в строке не изменён;
- обучение калибровки кусковатости на старом снимке → понятная ошибка;
  `ppv_residual` на нём учится;
- старые JSON артефактов и снимков (фикстуры до PR 3) грузятся без ошибки
  контрольной суммы;
- сценарий и дрейф с артефактом старой и новой базы;
- пространственная модель: старая считает физику `kuzram_legacy`, новая и
  «без модели» — `kuzram` 2.0.0;
- `settings_source_label("kuzram", …, "1.0.0")` — «старая модель»;
  фронт: метки в панели калибровок.

Правятся: `tests/test_fragmentation_ml_baseline.py` (заглушки PR 2 уходят),
тесты калибровки, датасетов, дрейфа и пространственной модели, где ожидается
отсутствие новых полей.

Не должны измениться: golden-файлы листа «Расчёт» и старых моделей
(`tests/fixtures/kuzram_cunningham_golden.json`,
`tests/fixtures/fragmentation_legacy_golden.json`), контракт настроек.

## 7. Порядок выката

1. Заплатка 4.1 — коммитом в #101 до его слияния.
2. PR 3 — одним PR от `main` после слияния #101 (до слияния — от ветки

   собрать новый снимок, обучить, перевести в production.

## 8. Риски

- **Калибровки кусковатости перестают действовать на новых прогнозах до
  переобучения.** Это решение № 3 владельца; риск — в сроке переобучения.
- **Пересчитанный baseline не равен тому, что видел инженер.** Намеренно:
  поправка учится относительно той формулы, к которой её прикладывают.
  Сохранённый прогноз остаётся в строке для разбора.
- **Настройки объекта менялись со времени взрыва.** Для прогнозов PR 2 и позже
  берётся снимок из прогноза; для более старых — текущие настройки объекта, с
  источником в строке снимка.
- **Сборка снимка дольше:** пересчёт движком на каждый взрыв. Движок считает
  блок за доли секунды; предел — число взрывов площадки.

## 9. Вне объёма

- Переобучение калибровок и пространственных моделей на проде.
- Умолчания породы и ВВ в «физике» пространственной модели (`DEFAULT_*`, не из
  паспорта) — прежняя слабость.
- `ppv_residual` и модели outcomes/learning (без baseline кусковатости).
- Пересчёт или перепись сохранённых прогнозов, снимков и артефактов.
