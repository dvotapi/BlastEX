## 1. Откуда факт и как он попадает в документы

**Где факт сейчас.** Факт бурения, заряжания и взрывания пишется в проект блока (`BlastDesign.as_drilled_holes`, `as_charged_holes`, `as_fired_holes`; `POST /design/as-drilled`, `/as-charged`, `/as-fired`, панели «Проектирования»). Это часть `EXECUTION_PAYLOAD_KEYS`: её правка не меняет `designed_sha256`, разрешена в статусах проекта блока `approved` и `executed`. Ревизия проекта МВ хранит снимок блока с `design_sha256` и факта не содержит.

**Предложение (В1): новый слой «Факт» (`EXECUTION`).** Ревизия проекта МВ подписана ролями (#113) и неизменяема; новая ревизия проекта ради факта сломала бы согласования, статусы (`approved → executed` без черновика) и пометку «устарел» у всех слоёв. Слой уже даёт всё нужное: перенос (`seed`), ручной ввод (`payload`), неизменяемые ревизии с `content_sha256`, пометку «устарел», выпуск только человеком, печать из ревизии. «Перевыпуск таблицы ревизией `executed`» (TASK §3.2) — это ревизия слоя «Факт», выпущенная, когда проект в статусе `executed`.

| | Слой «Факт» (`EXECUTION`) |
|---|---|
| Открывается | после `approved` (В2): факт бурения нужен до заряжания (п. 412, условие 1 акта готовности); перевыпуск — после заряжания и после взрыва |
| Сколько | один на проект |
| Перенос (`seed`) | по каждому блоку ревизии проекта: читается текущий проект блока; его `designed_sha256` обязан совпасть с `design_sha256` ревизии (иначе ошибка: факт относится к другой сетке); в `seed` — строки таблицы параметров Р из ревизии проекта (копия), факт по скважинам (§2), итоги Р и Ф, фактический расход ВМ (§4), точки Г.1 по съёмке и геометрия плана Г.1 из ревизии (§5), `execution_sha256` блока (хэш его `execution_payload`) |
| Ручной ввод (`payload`) | дата и время взрыва по факту, скважины-отказы (В7), примечания к скважинам по факту |
| Пометки | «устарел» — как у всех слоёв (новая ревизия проекта); «факт изменился» — `execution_sha256` блока сейчас другой, чем при переносе: предупреждение в слое, выпуск — ошибка до повторного переноса |
| Печать ревизии слоя | «Таблица параметров взрывных работ (исполнительная)» + Г.1 «Схема расположения скважин по исполнительной съёмке» — один документ, своя нумерация |

Расчёт факта — чистый модуль `design/mass_blast_fact.py`; читает проект блока и справочник ВМ ревизии проекта, проект блока не меняет (тест: `designed_payload` и `execution_payload` до и после равны).

Документы, которым нужен факт (акт приёмки, наряд после взрыва), берут его из **последней выпущенной ревизии слоя «Факт»** на той же ревизии проекта: в их `seed` — `fact` (сводка) и `execution_revision_id`. Слой «Факт» перевыпущен позже — у них предупреждение `fact_layer_stale` и перенос заново через прежний `refresh` (с расхождением до подтверждения). Талон-допуск от слоя «Факт» не зависит (В8): его выдают через 30 минут после взрыва, когда съёмки и записей заряжания ещё может не быть.

## 2. Графы «Ф» таблицы параметров

Факт печатается только у скважин, у которых есть соответствующая запись; нет записи — клетка Ф остаётся белой для записи от руки, в слое — предупреждение с перечнем (`fact_drilling_missing`, `fact_charging_missing`). Величины Ф считаются **теми же функциями, что Р**, на копии проекта блока с фактической геометрией.

| Графа | Ф | Как |
|---|---|---|
| Глубина, м | `as_drilled` | фактическая длина по оси (`AsDrilledHole.length_m`), 0,1 м |
| Перебур, м | `as_drilled` | В4: Δ_ф = L_ф − (Z_уст.ф − Z_подошвы) / cos α_ф, Z_подошвы = Z_уст.проект − H_у (`Hole.bench_height_m`); той же формулой L = (S − Z)/cos α + Δ, что у проекта (`geometry.hole_depth_m`) |
| ЛСПП, м | `as_drilled` | только первый ряд (тот же, что в Р): `toe_line.floor_burdens` на копии проекта с фактическими устьями и забоями (В5) |
| Между скважинами, м | `as_drilled` | `editing.local_spacing` в ряду по смешанной сетке: факт, где есть, иначе проект (В5) |
| Между рядами, м | `as_drilled` | `mass_blast_table._row_steps` по смешанной сетке (В5) |
| Масса заряда, кг | `as_charged` | `charge_mass_kg` записи; округление — В3 |
| Забойка, м | `as_charged` | над верхним зарядом по фактическим декам (`safety.holes._top_stemming`, как Р); дек нет — `stemming_length_m` записи |

- Итоговая строка: Ф-итог графы печатается, когда факт этой графы есть у всех включённых скважин; иначе клетка пустая (неполная сумма выглядела бы фактом).
- Примечание: к прежнему (действие «снизить заряд», ручное) добавляется «отказ» у скважин-отказов (В7) и ручное примечание по факту. Правило «общее для ≥ 60 % — в шапку» — прежнее.
- Шапка документа — «ТАБЛИЦА ПАРАМЕТРОВ ВЗРЫВНЫХ РАБОТ (ИСПОЛНИТЕЛЬНАЯ) · блок · гор.» и строка «Факт: бурение N из M, заряжание N из M скважин; дата и время взрыва …». Раскладка — та же, 63 / 73 строки на страницу.
- Записи факта, созданные копированием проекта (`provenance.method = "copy"`), — тоже факт (их записал человек), но в слое — предупреждение `fact_copied_from_design` с числом скважин (В6).

## 3. Талон-допуск

- В ручной ввод талона — `fired_date`, `fired_time` (фактические дата и время взрыва). «Не ранее» = факт + 30 мин (п. 422); без факта — как сейчас, проектное время + 30 мин с пометкой «по проекту». Считается при выпуске ревизии (в `view`), рендер печатает готовое.
- `as_fired.firing_timestamp` для времени взрыва не годится: при записи без времени это момент записи (`record_as_fired` ставит «сейчас»).
- Текст «отказавших зарядов нет» — как в форме (В7).

## 4. Наряд-путёвка после взрыва

Слой наряда уже печатает графы «Выдано», «Израсходовано», «Возвращено» и разд. 1 «Заряжено / Взорвано / Отказы / Отклонение» пустыми. PR 5 их заполняет — только для архивной копии (TASK §2.2: оригинал заполняется от руки и сдаётся на склад):

| Графа | Откуда (В9) |
|---|---|
| Разд. 1: заряжено скважин, фактически заряжено, кг | факт слоя «Факт» по блоку: скважин с записью заряжания, Σ `charge_mass_kg` |
| Разд. 1: взорвано зарядов, масса взорванных | заряжено − отказы (В7) |
| Разд. 1: отказы, шт | скважины-отказы слоя «Факт» |
| Разд. 1: отклонение факт − проект, кг | факт − проект |
| Разд. 2: израсходовано | ВВ — по маркам из `as_charged` (масса дек по марке, иначе `explosive_product` записи); ПД — по маркам из `as_charged.primer_items`; НСИ скважинные — по маркам из `as_fired.detonator`; поверхностные и стартеры — факта в BlastEX нет: вводятся вручную. Ручное значение главнее |
| Разд. 2: выдано | вручную (до MagEX, PR 7 — из `GET /naryads/{id}`) |
| Разд. 2: возвращено | выдано − израсходовано, если оба известны; иначе вручную; ВВ, изготавливаемые на месте (`vv_site`), — «—» (уже так) |

- Ручной ввод наряда расширяется словарями по ключу строки ВМ: `issued`, `consumed`, `returned`. Правка этих граф — только при проекте `executed` / `closed`.
- Сверка «выдано = израсходовано + возвращено» — предупреждение в слое `naryad_balance_mismatch`, на печать не идёт (графа «Контроль» и итоговые проверки — дело MagEX, TASK §2.2). Для `vv_site`: израсходовано ВВ ≠ выдано — предупреждение (остаток заряжается в крайние скважины).
- Факт на строку ВМ сопоставляется по коду материала справочника (`material_code` строки расхода), а не по подписи. Марка факта, которой нет среди строк проекта, — отдельная строка «вне проекта» с предупреждением `fact_material_not_in_project`.

## 5. Г.1 по исполнительной съёмке

Решение владельца В1 PR 4: Г.1 ревизии проекта остаётся по координатам проекта блока; по фактической съёмке — здесь.

- Второй лист документа слоя «Факт», тот же генератор (`plan_sheet`, листы PR 4) и то же правило масштаба и поворота (§3 плана PR 4); геометрия плана (контур, бровки, ситуация, линии разрезов) — копия `blocks_v2[i].graphics` ревизии проекта.
- Скважина с фактом бурения — по фактическому устью (наклонная — отрезок до фактического забоя), снизу фактическая глубина. Без факта — по проекту, пустым серым кружком, перечнем в примечании («по проекту, без съёмки: …»). Смещение устья больше 0,5 м (допуск условия 2 акта готовности) — номер красным и перечнем в примечании с величиной.
- Подпись «Съёмку выполнил: маркшейдер …» — из реквизитов проекта, пусто — пустая линия.
- Несколько блоков — лист на блок.
