## 2. Ключи, служебный токен, JWKS, клиент

### 2.1. Настройки (`api/config.py`, одно место)

| Переменная | Что |
|---|---|
| `BLASTEX_MAGEX_INTEGRATION_ENABLED` | флаг (§0) |
| `MAGEX_API_URL` | адрес MagEX до `/api/v1` (`https://…/api/v1`); без него при включённом флаге — режим «вне учёта MagEX» (§6) |
| `MAGEX_ORGANIZATIONS` | соответствие организации BlastEX → UUID организации MagEX, JSON `{"default": "…uuid…"}` (вопрос В1); организации нет в списке — «вне учёта MagEX» |
| `BLASTEX_SIGNING_KEY`, `BLASTEX_SIGNING_KID` | закрытый ключ ES256 (PEM, P-256) и его `kid` — секрет окружения |
| `BLASTEX_JWKS_EXTRA` | открытые ключи, которые публикуются, но не подписывают: следующий (ротация) и прежние (пока ходят бумаги с их QR), JSON `{"keys": [...]}` без `d` |
| `BLASTEX_ALLOW_TEST_KEY` | `true` — разрешает тестовый ключ MagEX (`TEST-ONLY-magex-fixture`) — только тесты и локальный стенд |

Проверки при старте (как у MagEX): ключ — EC P-256 с закрытой частью; в `BLASTEX_JWKS_EXTRA` нет `d` и повторов `kid`; **тестовый ключ узнаётся по отпечатку RFC 7638**, а не по `kid`, и без `BLASTEX_ALLOW_TEST_KEY=true` API не стартует. Флаг включён, а ключа нет — API стартует, слой в режиме «вне учёта MagEX» с предупреждением `magex_not_configured`.

### 2.2. Подпись строки — `design/magex/jws.py` (чистые функции)

- Содержимое: `json.dumps(..., ensure_ascii=False, sort_keys=True, separators=(",", ":"))`, UTF-8 без BOM, без `NaN`/`Infinity` (`allow_nan=False`), необязательное, которого нет, — **опущено** (не `null`): запись одна для всех переподписаний одной версии (контракт, разд. 3).
- Raw DEFLATE уровня 9 (`zlib.compressobj(9, DEFLATED, -15)`), base64url без `=`.
- Заголовок `{"alg":"ES256","kid":…,"typ":"naryad-v1"}`; подпись ECDSA P-256 SHA-256, DER → **R‖S 64 байта**.
- Длина строки ≤ 2 000 (`MAGEX_NARYAD_JWS_MAX_LENGTH`, по умолчанию 2 000): длиннее — сначала сокращаются `name` блоков до кода, не помогло — ошибка `magex_jws_too_long`, отправки и печати нет.

### 2.3. Служебный токен

JWT ES256 тем же ключом: заголовок `typ` = `blastex-service`; поля `iss` = `blastex`, `aud` = `magex` (строкой), `org` — UUID MagEX, `iat`, `exp` = `iat + 120`. Новый токен на каждый запрос (дёшево, и часы не подведут).

### 2.4. JWKS — `GET /.well-known/jwks.json`

Без входа (данные открытые), `Cache-Control: max-age=300`: текущий ключ + `BLASTEX_JWKS_EXTRA`, у каждого `kty`, `crv`, `x`, `y`, `kid`, `alg` = `ES256`, `use` = `sig`. Отдаётся, когда ключ задан, независимо от флага (MagEX должен увидеть ключ раньше, чем BlastEX начнёт подписывать). В `frontend/Caddyfile` — `handle /.well-known/jwks.json` → `api:8000`.

### 2.5. Ротация и выкладка (раздел в `Docs/MAGEX_INTEGRATION.md`)

Скрипт `scripts/magex_signing_key.py` создаёт ключ (PEM в файл с правами 600, в вывод — только открытый JWK и `kid`). Порядок: новый открытый ключ → в `BLASTEX_JWKS_EXTRA`, перезапуск → **не раньше чем через 330 с** — в `BLASTEX_SIGNING_KEY/KID`, прежний открытый → в `BLASTEX_JWKS_EXTRA` → прежний убирается, когда закрыты все наряд-путёвки с его QR (список — `GET …/magex/keys-in-use`, §5.6). Первая выкладка: ключ на VPS BlastEX → MagEX `VM_BLASTEX_JWKS_URL=https://<BlastEX>/.well-known/jwks.json` → через 330 с включить флаг.

### 2.6. Клиент — `api/services/magex_client.py`

`requests` (уже в зависимостях), тайм-аут 10 с, ответы разбираются по контракту (`code`, `message`, `details`). Методы: `materials()`, `availability(wh, material_ids)` (≤ 100 позиций), `report_status(blaster_ref)`, `put_naryad(id, jws)`, `cancel(id, ver, reason)`, `get_naryad(id)`. Исключения по видам: `MagexUnavailable` (сеть, тайм-аут, `5xx`, `503 BLASTEX_KEYS_UNAVAILABLE`) — повтор; `MagexRejected` (`409`, `422`, `404`) — с кодом и `details`; `MagexAuthError` (`401`, `403`) — ошибка настройки, показывается как есть. Строка JWS и токен в журнал не пишутся.

## 3. Справочники

### 3.1. ВМ ↔ позиции MagEX — `materials.magex_material_id`

- Новое поле `MaterialPayload.magex_material_id: UUID | None` — title «Позиция MagEX», description «Позиция номенклатуры MagEX для наряд-путёвки».
- В схеме — признак источника значений `x-options: "magex.materials"`: форма справочника (общая, по каталогу схем) показывает такое поле **списком** позиций MagEX («краткое наименование — наименование по Балансу ПВМ, единица»), а не полем UUID. Список — `GET /api/v1/mass-blast/magex/materials` (прокси `GET /materials` под служебным токеном организации). Без интеграции поле только для чтения с пояснением.
- Сопоставление ищется по коду материала строки наряда (`material_code` расхода проекта). Строка без кода или с несопоставленным материалом — ошибка слоя `magex_material_unmapped` (разрешить нельзя) со списком марок.
- Несколько строк наряда с одной позицией MagEX (например, одна марка НСИ в разных строках) — **складываются** в одну строку выписки (повторов позиций контракт не допускает).

### 3.2. Склад — `mass_blast_sites.magex_warehouse_id`

- Новое поле реквизитов объекта: UUID склада MagEX (title «Склад MagEX», description «идентификатор склада выдачи в MagEX»). Служебного списка складов в MagEX пока нет (контракт, разд. 10) — поле вводится текстом с проверкой формы UUID; правильность видна сразу в наряде: `GET /availability` с неизвестным складом → `404` → ошибка `magex_warehouse_unknown`.
- В слое наряда — `magex_warehouse_id` в ручном вводе: по умолчанию склад объекта; менеджер выбирает **из складов, указанных у объектов организации** (подпись — поле «Склад выдачи ВМ» того объекта). Текстовое поле «Склад выдачи» остаётся для печати.

### 3.3. Что ещё нужно контракту, а в BlastEX текстом — вопросы В2–В4

`blaster.ref` (UUID взрывника), `permit_vr` (`{number, date}`), `vehicle` (`{plate, model}`) — см. §12.

### 3.4. Объект и организация

`site.id` — UUID v5 от `blastex:site:<организация>:<код объекта>` (постоянный, без нового поля), `site.name` — наименование объекта. `org` — по `MAGEX_ORGANIZATIONS` (В1).

## 5. Разрешение, версии, очередь

### 5.1. Хранение (миграция 0015)

- `mass_blast_magex_versions`: `id`, организация, `layer_id`, `ver` (уникален в слое), `layer_revision_id` (ревизия слоя, которую версия печатает), `jws`, `kid`, `payload_sha256` (хэш содержимого без `iat` — для «без изменений»), `status` (`PENDING`, `ACCEPTED`, `REJECTED`, `SUPERSEDED`), `response_code`, `response` (тело ответа MagEX — для таблицы нехватки и ошибок по полям), `attempts`, `next_attempt_at`, кто и когда отправил, когда принята.
- `mass_blast_magex_naryads`: последнее известное исполнение слоя — `status`, тело `GET /naryads/{id}`, момент чтения (показ без связи и блокировки §7).

### 5.2. «Разрешить» — `POST …/layers/{id}/magex/approve` (`require_human`)

1. Проверки слоя (как у выпуска: не «устарел», нет ошибок) и интеграции (ключ, организация, склад, сопоставление ВМ, взрывник, начальник участка, длина строки). Ошибки — списком с `path` к полю.
2. `ver` = наибольшая отправленная версия слоя + 1 (под блокировкой строки слоя: два нажатия не получат один номер). Неотправленная версия в очереди с меньшим `ver` → `SUPERSEDED` (её повтор дал бы `NARYAD_VERSION_OUTDATED`).
3. Собрать содержимое, подписать, `PUT /naryads/{id}`.
4. По ответу:
   - **`200`** — версия `ACCEPTED`; выпускается ревизия слоя (`issue_layer`) со снимком `magex` = `{ver, kid, jws, wh, accepted_at}`; запоминается исполнение из тела ответа. Только теперь слой «разрешена», доступна печать.
   - **`409` / `422` / `404`** — версия `REJECTED`, ревизии слоя нет (как и у MagEX, отказ ничего не оставляет). В окне: `INSUFFICIENT_AVAILABLE` — таблица «позиция / нужно / доступно» (по `details.lines`, в единице наряда); `NARYAD_NUMBER_TAKEN` — у поля «№»; `NARYAD_LOCKED` — по подкодам у полей (склад, взрывник, дата, позиции); `422` — `details.errors` у полей; `VERSION_CONFLICT/OUTDATED` — «в MagEX версия N, обновите исполнение».
   - **`503`, сеть, `5xx`** — версия `PENDING`, ревизия слоя выпускается сразу (содержимое уже подписано и не меняется), но **печать закрыта**, в окне «ожидает MagEX» и время следующей попытки.
   - **`401`/`403`** — ошибка настройки: версия `REJECTED`, текст — «MagEX не принял вход BlastEX: проверьте ключ и организацию».
5. Без включённой интеграции кнопки нет — выпуск ревизии как в PR 6.

### 5.3. Очередь повтора

Фоновая задача в процессе API (запускается в `lifespan`, если флаг включён): раз в 30 с берёт версии `PENDING` со сроком попытки (`FOR UPDATE SKIP LOCKED` — несколько процессов не отправят одну версию дважды) и шлёт **ту же строку** (повтор идемпотентен: принятая — `200` «без изменений»). Отступ: 30 с, 1, 2, 5, 10, 30, 60 мин, дальше раз в час, пока версию не примут, не отклонят или не заменят новой. В окне — «Повторить сейчас». `NARYAD_SIGNATURE_INVALID` сразу после ротации — повтор не раньше 330 с (контракт, разд. 7 п. 3), иначе — `REJECTED`.

### 5.4. Отмена — `POST …/magex/cancel` (`require_human`, причина обязательна, ≤ 500)

`POST /naryads/{id}/cancel` с текущей принятой версией. `409 NARYAD_ALREADY_ISSUED` — «ВМ уже выданы: наряд закрывается на складе (полный возврат, расход 0)». Возврат проекта в черновик или новая ревизия проекта сами ничего в MagEX не отменяют и не отправляют (слой «устарел» — §2.1 задачи): у слоя с принятой невыданной версией — предупреждение `magex_naryad_active` с кнопкой «Отменить в MagEX» (В10).

### 5.5. Повтор той же версии

Повторное «Разрешить» без изменений содержимого (тот же `payload_sha256`, что у последней принятой) новую версию не создаёт: отправляется принятая строка, ответ `200` «без изменений» — так проверяется связь и обновляется исполнение.

### 5.6. Ключи в ходу

`GET /api/v1/mass-blast/magex/keys-in-use` (админ): `kid` → число принятых версий с незакрытыми наряд-путёвками (по последнему известному статусу). Нужен, чтобы убрать старый ключ (§2.5).

## 6. Печать (форма 4)

- Ревизия слоя с принятой версией: **QR — та же строка JWS**, что ушла в `PUT`; в правом верхнем углу формы 4, 40 × 40 мм, уровень коррекции L, без масштабирования (`/PrintScaling /None`); под ним мелко «№ {num} / версия {ver} / {склад}». Раскладка формы 4 не меняется: QR — в поле шапки справа от заголовка.
- Ревизия с версией `PENDING` или `REJECTED` — PDF не отдаётся (`409`: «наряд-путёвка не принята MagEX»), предпросмотр черновика — можно, с пометкой «ЧЕРНОВИК».
- Флаг включён, но интеграция не настроена (нет адреса, ключа или организации) — ревизия выпускается как раньше, снимок получает `magex` = `{"mode": "OFFLINE"}`, в шапке мелко «вне учёта MagEX».
- Графа «Контроль» и итоговые проверки — не заполняются (как в PR 3–6: графа пустая, раскладка не меняется).
- Ревизии, выпущенные до PR 7 и при выключенном флаге, — без ключа `magex`, печать байт-в-байт прежняя (тест хэшем PDF).

## 7. Окно наряда: доступность, взрывник, исполнение, блокировки

- **«Доступно на складе»** — четвёртая графа таблицы ВМ: `GET …/layers/{id}/magex/availability` (сервер сам переводит в единицу строки наряда: шт ↔ кг по `unit_mass_kg`) при открытии слоя и после правки запаса (с задержкой 0,5 с). Нехватка («к выдаче» > «доступно») — подсветка строки до отправки; под таблицей — «остаток на {момент расчёта}». Нет связи — «—» и «MagEX недоступен», без запрета.
- **Взрывник** — при выборе `GET /blasters/{ref}/report-status`: есть неотчитанные — предупреждение `blaster_not_reported` со списком (№, дата выписки, объект). Не запрет. Допуски — ручное подтверждение начальника участка (галочка «Допуски взрывника, водителя и автомобиля проверены», обязательна для «Разрешить»), пока нет источника SafetyMAIN.
- **Исполнение** — `GET /naryads/{id}` при открытии слоя и по «Обновить»: статус («разрешена», «ВМ выданы», «возвращено», «расход по фото», «закрыта», «отменена»), по позициям «выписано / выдано / возвращено / израсходовано / утрачено / на руках» (ед. и кг), выданные партии, `block_results`. Последний ответ хранится (§5.1) — без связи показывается он с моментом чтения.
- **Блокировки после выдачи** (`issued` и дальше по последнему известному статусу): в форме только для чтения — склад, взрывник (ФИО, индекс, `ref`), дата выписки, запас (он меняет количества), а также № и подтверждение допусков (бумага на руках); сервер отклоняет такие правки (`magex_field_locked`). Перенос данных проекта разрешён, но если он меняет состав или количества позиций, «Разрешить» недоступно: «ВМ выданы — нужна новая наряд-путёвка» (кнопка «Ещё наряд-путёвка» уже есть с PR 6).
- **После взрыва** (В7): графы «выдано / возвращено / израсходовано» берутся из исполнения MagEX (источник «MagEX»), разд. 1 по блокам — из `block_results`; расхождение с фактом заряжания BlastEX — предупреждение. Печать архивной копии ревизией `executed` — из них.

## 10. Тесты

- **Контракт** — фикстуры MagEX копируются в `tests/fixtures/magex/` (как есть, с `README` о происхождении и SHA MagEX):
  - в тестах — строгая проверка строки по разд. 1 контракта (порядок шагов, R‖S, `typ` с регистром, `crit`, канонический base64url, распаковка ≤ 64 КиБ, хвост после потока, повтор ключа); **19 векторов** дают ожидаемые коды — значит, проверка верна;
  - наша строка проходит ту же проверку тестовым набором ключей и схему `naryad.v1.schema.json` (`jsonschema` — только тестам, ставится в CI, как `pypdfium2`), а также «серверные» правила разд. 2 (`qty` > 0, без повторов, `blast_on` ≥ `on`, `approved.at` с поясом);
  - `sample.jws` распаковывается в `sample.json`; переподписание той же версии даёт тот же хэш содержимого.
- **Наряд блока 66** (§7 задачи): 5 блоков-строк в печати, позиции «по проекту + запас», строка ≤ 2 000; запас 50 кг ВВ и 5 ПД меняет `qty`, но не зоны и Q_э.
- **Клиент и разрешение** — заглушка MagEX в процессе (`httpx` транспорт/`requests` адаптер): `200` → ревизия и печать; `409 INSUFFICIENT_AVAILABLE` → нет ревизии, таблица нехватки; `NARYAD_NUMBER_TAKEN`, `NARYAD_LOCKED`, `422` → ошибки по полям; `503` и обрыв → `PENDING`, повтор той же строки, затем `200`; новая версия заменяет ожидающую; блокировки после `issued`.
- **Служебный токен и JWKS** — поля и заголовок, срок ≤ 300 с; тестовый ключ без разрешения — отказ старта; JWKS без `d`.
- **Печать** — QR декодируется обратно в ту же строку (по растру `pypdfium2` + декодер — если в CI нет декодера, сверка содержимого виджета); PDF ревизий без `magex` — тот же хэш.
- **Интеграционный** — `tests/test_magex_live.py` против локального Compose MagEX (`docker compose up`, сид `--scenario`, тестовый ключ): `PUT` → `200`, резерв = «Выписано», повтор → «без изменений», нехватка → `409`. Пропускается без `MAGEX_LIVE_URL`; гоняю локально, в CI его нет.
- Фронт: `vitest` формы наряда (графа, блокировки, состояния, таблица нехватки), `tsc -b`; полный `pytest` локально (PG — временный `postgres:16-alpine`).

## 12. Вопросы владельцу

**В1. Организация MagEX.** В BlastEX организация — строка (`default`), в MagEX — UUID. Предлагаю переменную `MAGEX_ORGANIZATIONS` = `{"<организация BlastEX>": "<UUID организации MagEX>"}`; организации нет — наряд «вне учёта MagEX». UUID dev-организации MagEX — `00000000-0000-4000-8000-00000000d0e1`; прод — от вас.

**В2. Взрывник (`blaster.ref`).** Контракт требует постоянный UUID взрывника (SafetyMAIN); в BlastEX взрывник — ФИО в персонале проекта, индекс — в наряде. После выдачи `ref` менять нельзя (`BLASTER_LOCKED`). Предлагаю раздел справочника **«Взрывники»** (ФИО, индивидуальный индекс, № единой книжки, сотрудник SafetyMAIN — UUID, пусто — BlastEX присваивает постоянный UUID по организации и индексу); роль «взрывник» в персонале и в наряде — выбор из списка, индекс подставляется. Альтернатива — без справочника, UUID по индексу из наряда (опечатка в индексе = другой взрывник).

**В3. Разрешение на ВР.** В реквизитах объекта — одной строкой; контракту нужны № и дата. Предлагаю два поля в реквизитах объекта и в наряде: «Разрешение на ВР: №» и «… дата»; прежняя строка остаётся запасной для печати. Альтернатива — разбирать строку «№ … от ДД.ММ.ГГГГ», не разобралось — без `permit_vr` с предупреждением.

**В4. Спецавтомобиль.** Сейчас «марка и гос. номер» одной строкой; в контракте — `plate` и `model`. Предлагаю два поля (марка, гос. номер) в реквизитах объекта и в наряде; прежняя строка — запасной в `model`.

**В5. Кто нажимает «Разрешить» и кто в `approved`.** Предлагаю: нажимает любой человек (`require_human`, не ключ API); в `approved` — начальник участка из персонала проекта (ФИО, должность; не заполнен — нельзя), момент — нажатие, с поясом. Альтернатива — как у согласования (#113): только учётка, назначенная на роль «начальник участка».

**В6. Патронированные ВВ.** В проекте — кг, в MagEX — штуки (патроны). Предлагаю округлять **вверх** до целых патронов и показывать это в строке («к выдаче 1 000 кг = 40 патр. по 25 кг»); «Выписано» в печати — по округлённому. Альтернатива — запрет с просьбой подобрать запас до целого числа патронов.

**В7. Исполнение MagEX против ручного ввода и факта.** Предлагаю: после взрыва «выдано / возвращено / израсходовано» наряда — из MagEX (главнее ручного ввода; ручной ввод этих граф закрывается, пока MagEX отвечает), разд. 1 — из `block_results`, расхождение с фактом заряжания BlastEX — предупреждение; графы «Ф» таблицы параметров по скважинам — по-прежнему из факта заряжания проекта блока; акт приёмки — фактический ВВ из MagEX («израсходовано» ВВ), когда расход внесён, иначе из «Факта».

**В8. Флаг и выкладка.** Флаг выключен по умолчанию; включаете вы после: ключ на VPS BlastEX (скрипт §2.5), `VM_BLASTEX_JWKS_URL` в MagEX, `MAGEX_API_URL` и `MAGEX_ORGANIZATIONS` в BlastEX, 330 с. Подходит? Нужен адрес MagEX на проде и доступ BlastEX → MagEX по сети (оба на одном VPS?).

## 13. Решения по умолчанию (если не возразите)

- `site.id` — UUID v5 от организации и кода объекта (§3.4), без нового поля.
- `name` блока — «Блок {код}»; пустые строки разд. 1 в выписку не идут.
- Повторное «Разрешить» без изменений — повтор принятой строки, не новая версия (§5.5).
- Ревизия слоя при `503` выпускается сразу, печать закрыта до `200` (§5.2).
- Склад выдачи — только из складов, указанных у объектов организации (§3.2), пока у MagEX нет списка складов для служебного токена.

## 14. Отступления при реализации

- Маршруты — под роутером проекта МВ: `/api/v1/design/mass-blast-projects/magex/…` и `…/layers/{id}/magex/…`, а не `/api/v1/mass-blast/…` (§8): так они под тем же флагом и проверками доступа, что и слои.
- MagEX недоступен в момент «Разрешить»: содержимое собирается по номенклатуре последнего чтения (окно наряда читает её при открытии), версия встаёт в очередь; номенклатуру не читали ни разу — «Разрешить» отказывает с причиной.
- Печать ревизии наряда — только **последней** принятой версии и только пока наряд не отменён в MagEX (QR старой или отменённой версии склад не примет; находка автоматической проверки безопасности).
- Состояние MagEX в окне получает наименования позиций (`material_names`) из снимка принятой ревизии — таблица исполнения без идентификаторов MagEX.
- Живой тест (`tests/test_magex_live.py`) — против отдельного Compose MagEX (`docker compose -p magex-blastex-pr7`, свои порты), чтобы не трогать данные стенда MagEX владельца.
- Живой стенд выявил ответ MagEX, которого нет в README контракта: `409 BLASTER_INDEX_CONFLICT` — индекс взрывника в справочнике MagEX связан с другим сотрудником. Окно показывает его с подсказкой указать того же «Сотрудника SafetyMAIN»; живой тест проверяет отказ и приём с тем же сотрудником.
- Стенд MagEX для живого теста — образ `magex-backend:latest` (сборка из исходников на этой машине не скачала базовый образ); приём, резерв, повтор, нехватка, отмена на нём проходят.
