# Единые справочники в project1 и обмен со схемой public

Дата: 2026-09-03. Статус: согласовано с владельцем в обсуждении, ждёт реализации.

Связанные документы: `TASK-002.md` (единый контур расчётов), `TASK-008.md`
(единое хранилище PostgreSQL), `Docs/REFERENCES_MODEL.md` (модель разделов),
`Docs/public_schema.sql` (DDL схемы `public` базы `project1`).

## 1. Проблема

В приложении два независимых хранилища справочников:

- Cost V1: файл `data/teams/<team>/references.json` (объекты работ, станки,
  породы, ВМ, амортизация) и `snapshot` рабочего пространства (номенклатура,
  постоянные расходы, должности). Их читают вкладки «Расчёт БВР → смета»,
  «Бурение», «Персонал», «Экономика» и страница «Справочники расчёта».
- Cost V2: схема `blastex` в PostgreSQL `project1`, таблицы
  `reference_items` и `reference_revisions`. Их читают страница
  «Справочники», панель технических паспортов и «Экономика блока».

Синхронизации нет. Перенос V1 → V2 предусмотрен только разовым скриптом
`scripts/import_cost_v1_to_project1.py`, который сейчас не проходит валидацию
из-за битых ссылок между разделами.

База `project1` общая для нескольких систем организации. В схеме `public`
живёт журнал буровых работ: объекты, контрагенты, договоры, техника, буровой
инструмент, средства инициирования с ценами по спецификациям, сотрудники,
смены. Владелец хочет, чтобы объект или ТМЦ, заведённые в BlastEX, появлялись
в `public`, а записи из `public` появлялись в BlastEX.

## 2. Цель и границы

Цель: один источник справочных данных для всех вкладок BlastEX — схема
`blastex` в `project1`; двусторонний обмен с таблицами `public`, у которых
есть смысловой аналог в BlastEX; зеркалирование остальных разделов в
`public` по схеме раздела; импорт и экспорт справочников файлом.

Не входит в задачу:

- отказ от движка Cost V1 и его вкладок (они остаются и читают данные из
  `project1` через адаптеры);
- паспорта проектирования `data/teams/<team>/designs/` — не справочники,
  остаются на файлах до отдельного решения;
- обмен с `public.employees`, `public.contracts`, `public.service_prices` и
  журналом смен — это не справочники экономики;
- произвольное конструирование таблиц из интерфейса: в `public` создаются
  только зеркала разделов blastex по их схемам;
- выдача прав роли `blastex` на схему `public` — делает администратор базы по
  подготовленному скрипту, приложение прав не меняет.

## 3. Архитектура

```
                 ┌──────────────────────────────────────────────┐
                 │ PostgreSQL project1                          │
                 │                                              │
  React ── API ──┤ blastex.reference_items / reference_revisions │
                 │        │  публикация (одна транзакция)        │
                 │        ├──► public.sites, counterparties, …   │  ◄── журнал
                 │        │    (сопоставление полей, §4)         │      буровых
                 │        └──► public.blastex_<раздел>           │      работ
                 │             (зеркало по схеме, §5)            │
                 │ blastex.public_links, public_mirror_sections  │
                 │ blastex.legacy_workspace_settings, …          │
                 └──────────────────────────────────────────────┘
```

Компоненты:

- `cost/v2/legacy_adapter.py` — опубликованная ревизия → структуры Cost V1
  (§6).
- `cost/v2/public_sync/` — сопоставление разделов blastex с таблицами
  `public` (§4) и зеркала разделов (§5). Пакет не знает об интерфейсе; всё,
  что нужно фронту, идёт через `api/`.
- `cost/v2/reference_files.py` — экспорт и импорт снимка справочников в xlsx
  и JSON (§8).
- Репозиторий `PostgresEconomicsRepository` расширяется методами хранения
  настроек рабочего пространства и сценариев сметы (§7).

Принципы:

- Публикация ревизии остаётся единственной точкой записи справочников.
  Выгрузка в `public` выполняется внутри той же транзакции: либо всё, либо
  ничего.
- В `public` никогда не выполняется `DELETE`; деактивация — `is_active =
  false`.
- Получение из `public` никогда не меняет черновик молча: сервер считает
  разницу, пользователь применяет её кнопкой и публикует обычным путём.
- Поля payload описываются только схемами `cost/v2/schemas/`; новые поля для
  обмена добавляются в схемы, а не в код обмена.

## 4. Обмен с существующими таблицами public

### 4.1. Сопоставление

| Раздел blastex | Таблица public | Направление |
|---|---|---|
| `sites` | `sites` | обе |
| `counterparties` | `counterparties` | обе |
| `equipment_types` | `equipment_models` + `machine_types` | обе |
| `equipment_assets` | `equipment_units` | обе; `status` только из public |
| `materials` с видом `СИ` | `initiating_device_types` | обе |
| `materials` с видом `Буровой инструмент` | `tool_types` | обе |
| `material_prices` | `explosive_material_prices`, `explosive_spec_items`, `explosive_purchase_specs` | только из public |

Поля, участвующие в обмене (далее «общие поля»):

`sites`: `name ↔ full_name`, `short_name ↔ short_name`, заказчик
`customer_code ↔ client_legal_name` (через контрагента), порода `rock_code ↔
mineral_type` (по имени породы), `is_active ↔ is_active`.

`counterparties`: `name ↔ full_name`, `inn ↔ inn`, роль: `CUSTOMER ↔
is_client`, `SUPPLIER`/`SUBCONTRACTOR ↔ is_supplier`, `is_active ↔
is_active`. Если в `public` контрагент одновременно клиент и поставщик, в
blastex он получает роль `CUSTOMER`, при выгрузке обратно флаг `is_supplier`
не сбрасывается.

`equipment_types`: `name ↔ model_name`, `brand ↔ brand`, вид техники `kind ↔
machine_types.name` по словарю в коде (`Буровой станок → DRILL_RIG`, `СЗМ →
SZM`, `Спецавтомобиль → HAZMAT_TRUCK`, `Легковой → LIGHT_VEHICLE`, `Трактор →
TRACTOR`); неизвестный тип машины из `public` не переносится и попадает в
предупреждения. Мощность двигателя и масса из `public` не переносятся.

`equipment_assets`: `inventory_number ↔ internal_id`, `serial_number ↔
serial_number`, тип `equipment_type_code ↔ model_id` через связь типа,
`is_active ← status <> 'Списано'`. Статус в `public` приложение не меняет:
им управляет журнал.

`materials` (СИ): `name ↔ name`, `comment ↔ description`; `material_kind =
СИ`, `storage_class = NSI` при создании из `public`.

`materials` (буровой инструмент): `name ↔ name`, `comment ↔ description`,
`lifetime_m ↔ expected_lifetime_meters`, `diameter_mm ↔ diameter`;
`material_kind = Буровой инструмент` при создании из `public`.

`material_prices` (только из public): для каждой активной строки
`explosive_material_prices` создаётся или обновляется цена с `material_code`
по связи типа СИ, `supplier_code` по контрагенту договора, `price_rub =
price_per_unit_base / unit_conversion_factor`, `valid_from`, `valid_to`. Код
цены: `PRICE_PUB_<id>`.

### 4.2. Новые поля схем

Добавить в схемы, потому что без них обмен теряет данные:

- `SitePayload.short_name: str | None`, до 5 символов (длина колонки
  `public.sites.short_name`), подпись «Краткое имя»;
- `EquipmentTypePayload.brand: str | None`, подпись «Марка»;
- `EquipmentAssetPayload.serial_number: str | None`, подпись «Заводской
  номер»;
- `MaterialPayload.lifetime_m: Decimal | None` («Ресурс», `x-unit: м`) и
  `MaterialPayload.diameter_mm: Decimal | None` («Диаметр», `x-unit: мм`).

Поля, нужные адаптеру Cost V1 (§6): `MaterialPayload.density_t_m3`
(«Плотность ВВ», `т/м³`), `RockPayload.ucs_mpa` («Прочность на сжатие»,
`МПа`), `RockPayload.fissuring_ff` («Трещиноватость», `трещин/м`).

### 4.3. Связи записей

Таблица `blastex.public_links` (миграция Alembic):

| Колонка | Тип | Назначение |
|---|---|---|
| `organization_id` | varchar(120) | организация blastex |
| `section` | varchar(64) | раздел blastex |
| `code` | varchar(120) | код записи |
| `public_table` | varchar(64) | таблица `public` |
| `public_id` | integer | первичный ключ в `public` |
| `synced_at` | timestamptz | время последней сверки |

Уникальны пары (`organization_id`, `section`, `code`) и (`public_table`,
`public_id`). Связь создаётся при первом переносе в любую сторону. Для
записей `public`, у которых ещё нет связи, код blastex образуется как
`PUB_<TABLE>_<id>` (например `PUB_SITE_12`); имя пользователь может менять,
код остаётся.

### 4.4. Получение из public

`POST /api/v1/economics/references/public-delta` принимает разделы
черновика (как `validate`) и возвращает разницу между `public` и черновиком.
Для каждой сопоставленной таблицы:

- запись без связи → предложение «новая» с готовой записью blastex;
- запись со связью, у которой общие поля отличаются от черновика →
  предложение «изменена» со списком полей, старым и новым значением;
- `is_active = false` в `public` при активной записи blastex → предложение
  «деактивирована».

Страница «Справочники» запрашивает разницу при загрузке и по кнопке
«Проверить project1». Если разница непустая, показывается плашка «Из
project1: N новых, M изменённых, K деактивированных» с кнопкой «Применить в
черновик». Применение меняет только черновик; строки видны в различиях и
публикуются обычной кнопкой. Ошибка доступа к `public` показывается в
плашке, остальная страница работает.

### 4.5. Выгрузка в public

Внутри `publish_references`, после записи ревизии и до фиксации транзакции:

1. Для каждой сопоставленной записи ревизии найти связь. Нет связи → `INSERT`
   в `public`, создать связь. Есть связь → сравнить общие поля с текущей
   строкой `public`; при различии `UPDATE` только общих полей. Совпадает →
   ничего (чтобы не трогать `updated_at` журнала).
2. Порядок: контрагенты, объекты, типы техники, основные средства,
   материалы — так внешние ключи `public` всегда находят родителя.
3. Записи, которые нельзя вставить из-за ограничений `public`, отклоняются
   на этапе валидации, а не в транзакции: контрагент без ИНН или с ИНН не по
   формату `^[0-9]{10}([0-9]{2})?$`, объект без заказчика (`client_legal_name
   NOT NULL`), основное средство без типа. Текст ошибки называет раздел, код и
   причину.
4. Любая ошибка записи в `public` откатывает публикацию целиком; ответ
   `HTTP 502` с текстом «Не удалось записать в project1.public: …».

Конфликт общих полей, когда запись изменена и в `public`, и в BlastEX:
побеждает публикация — пользователь видел плашку с разницей и осознанно
опубликовал. Материалы видов, кроме СИ и бурового инструмента, а также цены
в `public` не выгружаются.

## 5. Зеркала разделов в public

Для разделов, у которых нет аналога в `public` (породы, нормативы БВР,
условия бурения и любые будущие), администратор включает переключатель
«Выгружать в project1.public» на странице «Справочники». Состояние хранится
в таблице `blastex.public_mirror_sections` (`organization_id`, `section`,
`enabled`, `updated_at`, `updated_by`). Разделы из §4 зеркалами не
выгружаются.

Зеркало — таблица `public.blastex_<section>` (например
`public.blastex_rocks`), создаваемая приложением по Pydantic-схеме раздела:

- фиксированные колонки: `code text primary key`, `name text not null`,
  `is_active boolean not null`, `valid_from date`, `valid_to date`,
  `revision_id varchar(36) not null`, `synced_at timestamptz not null`;
- по одной колонке на поле схемы: `Decimal → numeric`, `bool → boolean`,
  `str`/`Literal` → `text`, `date → date`, ссылка (`x-ref`) → `text` с кодом,
  списки и вложенные модели → `jsonb`; поля с `x-internal` не выгружаются;
- комментарий колонки — `title` или `description` поля схемы.

При включении зеркала таблица создаётся, если её нет, включается RLS и
создаётся политика полного доступа для роли `blastex`, потому что событийный
триггер `public.rls_auto_enable` включает RLS на каждой новой таблице
`public`. Если у схемы раздела появилось поле — при следующей публикации
выполняется `ALTER TABLE ADD COLUMN`. Колонки никогда не удаляются и не
переименовываются; поле, ушедшее из схемы, остаётся в таблице пустым.

При каждой публикации содержимое включённых зеркал приводится к ревизии в
той же транзакции: строки вставляются или обновляются по `code`, отсутствующие
в ревизии получают `is_active = false`. Зеркало однонаправленное: записи,
внесённые в `blastex_<section>` другими системами, BlastEX не читает.

## 6. Адаптеры для движка Cost V1

Модуль `cost/v2/legacy_adapter.py` строит из `ReferenceSnapshot` структуры
Cost V1:

| Cost V1 | Источник в blastex |
|---|---|
| `WorkObject(name, mobilization_km, diesel_price_ton_rub)` | `sites` |
| `DrillRig(name, depreciation_per_shift_rub, fuel_l_per_h)` | `equipment_assets` с типом `DRILL_RIG` |
| `RockProperties(name, density_t_m3, ucs_mpa, fissuring_ff)` | `rocks` |
| `ExplosiveCatalogItem(key, name, density_t_m3, power_mj_kg)` | `materials` с видом `ВВ` |
| `FixedAssetDepreciation` | `equipment_assets` |
| `CatalogItem(id, name, category, unit, price, mass_kg, length_m)` | `materials` + `material_prices` |
| `FixedCostItem(id, section, name, amount_rub, enabled)` | `cost_items` с `legacy_section` |
| `JobPosition(id, name, fixed_salary_monthly, …)` | `positions` + `labor_rates` |

Отсутствующая запись или поле даёт предупреждение и значение по умолчанию,
а не исключение — как в модели себестоимости блока. Все места, где сейчас
читается `TeamReferences` из файла (`api/routers/workspace.py`,
`api/routers/references.py`, `api/services/cost_service.py`,
`api/services/converters.py`), переходят на адаптер. `cost/persistence.py`
теряет чтение и запись `references.json`; `cost/references_store.py`
удаляется.

Интерфейс: страница «Справочники расчёта» и её разделы удаляются вместе с
`PUT /references/*`; `GET /references/*` остаются только для чтения. Верхняя
панель «Объект работ» получает список объектов из состояния рабочего
пространства, которое сервер теперь собирает из `sites`. Из
`SaveWorkspaceRequest` уходит поле `references`.

Критерий: расчёт Cost V1 по эталонному сценарию команды `default` после
переезда совпадает с расчётом по файлам до копейки. Проверяется тестом на
зафиксированных ожидаемых суммах.

## 7. Настройки рабочего пространства и сценарии в БД

`legacy_workspace_settings` хранит имя команды, активный сценарий, активный
объект и ссылку на ревизию. Остальное состояние `WorkspaceSnapshot`
(назначения персонала, смен в месяц, ввод калькулятора бурения, переключатели
фаз) переезжает в `legacy_cost_scenarios.payload` по ключу сценария —
таблица уже создана миграцией 0002. Роутер `workspace.py` переходит на
методы репозитория; `data/teams/<team>/settings.json` и `scenarios/`
перестают читаться.

Каталог `data/teams` после переноса содержит только `designs/`; критерий
TASK-008 «`data/teams` не читается нигде, кроме скрипта импорта» уточняется:
кроме скрипта импорта и `design/persistence.py`.

## 8. Импорт и экспорт файлом

API:

- `GET /api/v1/economics/references/export?format=xlsx|json&revision_id=` —
  опубликованная ревизия (по умолчанию текущая) файлом;
- `POST /api/v1/economics/references/import` — multipart с файлом xlsx или
  JSON; ответ — разделы в формате `validate`, ничего не пишется в базу.

Формат xlsx: лист на раздел, имя листа — ключ раздела; строка 1 — ключи
полей (`code`, `name`, `is_active`, `valid_from`, `valid_to`, `comment`,
затем поля схемы), строка 2 — русские подписи из `title`/`description`,
данные с третьей строки. Ссылки — кодами, булевы — `да`/`нет`, даты —
датами Excel, списки и вложенные модели — JSON-строкой в ячейке. Импорт
читает ключи из строки 1 и не зависит от подписей; неизвестный лист или
колонка — ошибка с именем листа и колонки.

Формат JSON — тот же объект, что возвращает `GET /references/snapshot`.

Интерфейс: в панели публикации кнопки «Экспорт xlsx», «Экспорт JSON»,
«Импорт файла». Импорт заменяет в черновике разделы, присутствующие в файле,
остальные не трогает; далее обычный путь: проверка, различия, публикация.

## 9. Перенос данных

1. В `cost/v2/import_v1.py` исправить сопоставление, из-за которого сухой
   прогон не проходит: должности бригады (`POS_DRILLER`, `POS_BLASTER`,
   `POS_SZM_DRIVER`, `POS_WAREHOUSE_HEAD`) создавать в `positions`; материалы
   бурового инструмента (`MAT_BIT`, `MAT_HAMMER`, `MAT_RODS`, `MAT_CASING`)
   создавать в `materials`; статьи `MATERIAL_EXPLOSIVE`, `VM_DELIVERY`,
   `MATERIAL_NSI` создавать в `cost_items`; юнит `UNIT_1` сопоставлять с
   импортированным юнитом.
2. Скрипт получает `--sections a,b,c` для публикации части разделов и
   переносит настройки и сценарии в таблицы §7.
3. Порядок на VPS: резервная копия `data/teams`, сухой прогон, публикация,
   проверка расчёта, удаление всего из `data/teams`, кроме `designs/`.

## 10. Права и эксплуатация

Скрипт `scripts/grant_public_access.sql` для администратора базы:
`GRANT USAGE, CREATE ON SCHEMA public`, `GRANT SELECT, INSERT, UPDATE` на
таблицы §4.1 и `USAGE` на их последовательности, политики RLS полного доступа
для роли `blastex` на этих таблицах. Приложение прав не меняет и при их
отсутствии сообщает об этом текстом ошибки.

Локальная разработка: `Docs/public_schema.sql` загружается в контейнер
`blastex-pg-dev` вручную; тесты обмена используют переменную
`BLASTEX_TEST_DATABASE_URL`, разворачивают DDL в тестовой базе и
пропускаются, если переменная не задана.

- Настройки и сценарии: сохранение и чтение через репозиторий в памяти и в

## 12. Порядок реализации

Три отдельных PR в этом порядке; каждый самостоятельно проходит тесты:

1. Адаптеры, настройки и сценарии в БД, удаление файлового хранилища и

## 13. Риски

- Структура `public` принадлежит другой системе: изменение её колонок ломает
  обмен. Сопоставление полей собрано в одном модуле и покрыто тестами на
  DDL из `Docs/public_schema.sql`; при расхождении DDL тесты укажут место.
- Триггер `rls_auto_enable` и RLS-политики: без корректных политик роль
  `blastex` не увидит строк даже при наличии `GRANT`. Скрипт прав включает
  политики, проверка — тестом на тестовой базе с загруженным DDL.
- `public.sites.short_name` ограничен пятью символами; более длинные
  значения отклоняет валидация схемы, а не база.
- `equipment_models.model_name` уникален в `public`: два типа техники blastex
  с одинаковым именем не выгрузятся, валидация сообщит об этом до
  публикации.
